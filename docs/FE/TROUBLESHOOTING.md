## 1. BE/FE 포트 충돌 이슈

### 문제 정의
- BE와 FE가 백그라운드에서 동시 실행 시 충돌이 발생하여 한쪽 서버가 정상적으로 열리지 않음

### 사실 수집
- BE 포트: 3000
- FE 포트: 3000

### 원인 추론
- BE와 FE가 동일한 포트(3000)를 사용하도록 설정되어 있어, 하나의 프로세스가 포트를 선점하면 다른 프로세스가 해당 포트를 열지 못하고 충돌 발생

### 해결 및 검토
- **포트 변경**
  - FE 포트를 8080으로 변경
  - 변경 후 BE(3000), FE(8080)가 각각 독립적인 포트를 사용하여 백그라운드에서 정상적으로 모두 실행됨을 확인

## 2. FE API 요청 404 오류 (Proxy 누락)

### 문제 정의
- BE, FE를 각각 백그라운드에서 실행하였는데 FE에서 상품 정보 불러오기가 안 되고 로그인이나 회원가입도 안 됨

### 사실 수집
- 브라우저 콘솔에 다음과 같은 에러 발생:
   ```
  Failed to load resource: the server responded with a status of 404 (Not Found)
  home.js:202 HTTP error! status: 404` (`loadProducts @ home.js:202`)
  api/auth/me:1 Failed to load resource: the server responded with a status of 404 (Not Found)
  ```
- 프론트엔드 코드 내에서 API를 호출할 때 상대 경로(예: `/api/login`, `/api/products`)를 사용하고 있었으나, 프론트엔드 서버(`app.js`)에는 해당 경로의 요청을 백엔드로 넘겨주는(Forwarding) 프록시 설정이 누락되어 있었음

### 원인 추론
- 프론트엔드와 백엔드가 별도의 포트에서 동작하는 분리된 환경이기 때문에, 브라우저에서 상대 경로(`/api/...`)로 API를 호출하면 백엔드(3000번 포트)가 아닌 프론트엔드 서버 자신(8080번 포트)에게 데이터를 요청하게 됨
- 프론트엔드 서버는 단순 정적 파일만 서빙(`express.static`)하고 있을 뿐 API를 처리할 라우터나 DB가 없기 때문에, 해당 요청을 찾지 못하고 에러를 반환한 것임
- 즉, 프론트엔드(화면)로 들어온 요청 중 어떤 것이 정적 파일 요청이고 어떤 것이 백엔드 API 요청인지 구분하여 넘겨주는 길잡이(Proxy) 역할이 부재했던 것이 근본적인 원인으로 판단됨

### 해결 및 검토
- Proxy 설정 추가 및 특정 경로만 백엔드로 라우팅되도록 `pathFilter: '/api'` 옵션을 적용
- 적용 후 백그라운드에서 재시작하니 상품 정보 불러오기와 로그인/회원가입 모두 정상적으로 작동함을 확인

## 3. '나에게 선물하기' 버튼 클릭 무반응 현상

### 문제 정의
- **현상**: `product.html`(상품 상세 페이지) 하단의 '나에게 선물하기' 버튼을 클릭해도 주문 페이지(`order.html`)로 이동하지 않고 아무런 동작(무반응)이 일어나지 않음
- **기대 동작**: 버튼 클릭 시 사용자 로그인 상태를 검증한 후, 상품 ID와 함께 `order.html`로 라우팅되어야 함

### 사실 수집
- `product.html` DOM 확인 결과, 해당 버튼은 `<button id="btn-self-gift" class="btn-bottom-buy">` 구조로 하단 네비게이션에 하드코딩 되어 있었음
- `product.js` 이벤트 바인딩 확인 결과, `.btn-bottom-buy` 버튼에 클릭 이벤트가 연결되어 있었으나, 해당 핸들러 내부에서 `openBottomSheet()`라는 함수를 호출하고 있었음
- 하지만 현재 `product.html` 내에는 `bottom-sheet-overlay`나 `bottom-sheet-content` 관련 HTML 노드가 **존재하지 않음**

### 원인 추론
- 이전 개발 단계에서는 '구매하기' 클릭 시 뷰 하단에서 올라오는 바텀 시트(옵션 선택창 등)를 통해 최종 결제 페이지로 넘어가도록 기획/구현되었던 것으로 추정
- 이후 UI 기획이 변경되면서 바텀 시트 HTML 코드는 뷰(View)에서 제거되었으나, JS 로직에는 바텀 시트를 여는 코드 잔존
- 결과적으로 버튼을 누르면 존재하지 않는 DOM 요소를 열려다가 로직이 중단(Early Return)되어, 페이지 이동 명령인 `goToOrder()`가 단 한 번도 실행되지 않는 상태

### 해결 및 검토
  - `product.js`에서 더 이상 사용하지 않는 바텀 시트 관련 오픈/클로즈 로직 및 모바일 스와이프(Drag) 제어 잉여 코드 약 130여 줄을 완전히 제거
  - `.btn-bottom-buy` 요소 클릭 이벤트 핸들러 내부를 `goToOrder(productId, 'self');` 직접 호출로 대체
  - 코드를 수정한 후 '나에게 선물하기' 버튼 클릭 시, 정상적으로 `api/auth/me`를 통해 로그인 여부를 묻고 `order.html?productId=X&type=self` 경로로 전환됨을 확인
  - 무의미한 이벤트 리스너 제거로 메모리 누수를 방지하고 스크립트 실행 환경 최적화

## 4. 스크립트 로딩 순서 문제로 인한 버튼 미동작

### 문제 정의
- `component.js`는 `defer`로 로드되는데, 같은 페이지의 `complete.js` / `giftbox.js`는 `defer`가 없음
- 그 결과 뒤로가기 버튼(`#btn-back`), 검색 버튼(`#btn-search-open`)이 클릭해도 반응하지 않음

### 사실 수집
- `complete.js`: 즉시 실행 (defer 없음)
- 파싱이 끝난 뒤 `component.js` 실행 (defer)
- `DOMContentLoaded` 이벤트 발생
  - A 실행: `getElementById('btn-back')` 호출
  - B 실행: 헤더 주입(`#btn-back` 생성)

### 원인 추론
- 헤더가 만들어지기 전에 버튼을 찾으려고 해서 조용히 실패

### 해결 및 검토
- `component.js`가 헤더 주입을 끝낸 직후 커스텀 이벤트를 dispatch하고, 페이지 스크립트는 `DOMContentLoaded` 대신 이 이벤트를 구독하도록 변경

## 4-1. 추가 검토 및 수정 내용

### 문제의 근본 원인 재확인
- `component.js`는 defer로 로드되지만, `complete.js`와 `giftbox.js`는 defer 속성이 없었음
- 브라우저가 HTML을 파싱하다가 스크립트를 만나면 즉시 실행해 버렸기 때문에 순서가 꼬이는 문제

### 추가로 발견된 버그 (하단 네비게이션)
- `complete.js`와 `giftbox.js` 파일 맨 아래쪽에 하단 네비게이션 바(`.nav-item`)의 클릭 이벤트를 등록하는 코드가 있었음
- 이 코드가 이벤트 리스너(기존 `DOMContentLoaded`, 현재 `header:ready`) 바깥에 위치해 있었음
- 네비게이션 바 역시 `component.js`에서 동적으로 주입하고 있었기 때문에, 이 상태로는 하단 네비게이션 버튼을 눌러도 반응하지 않는(이벤트가 등록되지 않는) 동일한 타이밍 버그가 발생

### 최종 해결 조치
- `complete.js`와 `giftbox.js` 파일 하단에 있던 네비게이션 바(`.nav-item`) 이벤트 등록 로직을 모두 `header:ready` 이벤트 리스너 내부로 이동
- 이를 통해 `component.js`가 헤더와 네비게이션 바를 모두 화면에 그린 직후 `header:ready` 이벤트를 발생시키고, 그때서야 버튼들을 찾아 이벤트를 완벽하게 바인딩하게 됨

## 5. 로컬 개발 환경 DB 연결 타임아웃 (ETIMEDOUT) 에러

### 문제 정의
- 로컬 환경에서 백엔드(BE) 서버 구동 후, 프론트엔드(FE)에서 로그인 등 DB를 참조하는 API를 호출하면 `500 Internal Server Error`가 발생함
- 백엔드 콘솔 창에 `Error in POST /api/auth/login: Error: connect ETIMEDOUT` 에러가 지속적으로 출력되며 데이터베이스 연결이 실패함

### 사실 수집
- 에러 로그 확인: `connect ETIMEDOUT` (서버 접속 응답 시간 초과)
- 서버 인프라 상태 확인
  - AWS 서버: 현재 iwinv로 이전이 완전 종료되어 더 이상 응답하지 않는 폐기된 서버임
  - iwinv 서버: 보안 방화벽 설정으로 인해 실제 BE 서버 인스턴스에서의 접근만 허용되며, 외부(팀원 개인 로컬 PC의 사설 IP 등) 접속은 원천 차단되어 있음

### 원인 추론
- 로컬 BE 서버가 접근 불가능한 '원격 공용 DB'를 바라보도록 `.env`가 잘못 설정되어 있음
- 이전 AWS 서버는 이미 폐기되어 응답이 없고, 새 iwinv 서버는 방화벽에 의해 로컬망에서의 접근을 거부하고 있으므로 결국 네트워크 연결 대기 시간 초과(`ETIMEDOUT`) 에러가 발생한 것임

### 해결 및 검토
- 로컬 개발 시 공용 DB 접속은 불가능하므로, 팀원 각자의 개인 로컬 환경에 MySQL을 구축하고 연결하도록 가이드 및 설정 변경
- **로컬 DB 구축 및 데이터 이관**
  - 로컬에 MySQL 설치 및 `iksanshop` 데이터베이스 생성 (`utf8mb4` 캐릭터셋 적용)
  - BE 레포지토리 내의 `db/schema.sql`과 `db/seed.sql`을 실행하여 스키마 구조와 초기 테스트 데이터를 로컬에 세팅
- **환경 변수(.env) 수정**
  - `DB_HOST`를 기존 원격 IP에서 `localhost`로 변경
  - `DB_PASSWORD` 등 인증 정보를 본인의 로컬 MySQL 계정 정보로 변경
  - 원격 서버 주소는 `.env` 파일에서 완전히 삭제

- **검토**
  - BE 서버 재구동(`npm run dev`) 시 DB 에러 로그 없이 정상적으로 포트가 열리는 것 확인
  - FE 로컬 환경에서 로그인 API 재요청 결과, 정상적으로 DB 조회가 이루어지며 로그인 성공 확인
