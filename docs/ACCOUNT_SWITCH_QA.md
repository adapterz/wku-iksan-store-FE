# 계정 전환 후 이전 화면 정리 (#138 보완 목록 4번)

## 범위

- FE develop `62fee10` 기준. 찜 목록·찜 버튼, 선물함, 선물 도착 알림, 주문 완료 화면의 계정 전환 보완.
- 공통 처리는 기존 `component.js` 안에 유지한다. BE API·스키마·운영 데이터 변경은 없다.
- 합계/유효기간 표시 정책, 프로필 오류 코드 매핑, 관리자 신고 목록은 이번 범위에서 제외한다.

## 처리 방식

1. `/api/auth/me`의 `userId`와 조회 세대로 화면 소유자를 구분한다. 동시 인증 확인은 한 요청을 공유한다.
2. 탭 숨김/복귀·포커스 복귀·bfcache 복원 시 이전 응답을 무효화하고 개인 목록·모달·캐시를 정리한다. 같은 계정이어도 포커스 복귀마다 재조회한다. 서버 확인 전 이전 계정의 내용을 노출하지 않기 위한 보수적 처리이며, 목록/아이콘이 잠시 비워질 수 있다. 실제 브라우저에서 alert 종료·개발자도구 복귀 시 발생하는 포커스 이벤트 빈도는 별도 확인이 필요하다.
3. 확인된 계정으로 다시 조회한다. 네트워크/서버 오류는 로그아웃으로 처리하지 않고 재시도 안내와 **새로고침하여 다시 시도** 버튼을 표시한다. 버튼은 페이지 전체를 새로고침하며, 자동 반복 요청은 하지 않는다. 탭 복귀를 통한 기존 재확인도 유지한다.
4. 찜 변경·알림 확인·선물 카드/리뷰 진입 직전 계정을 재확인한다. 변경됐다면 기존 클릭을 새 계정으로 재실행하지 않는다.
5. 늦게 도착한 조회/변경 응답은 소유자·세대를 확인한 뒤 반영한다. 이전 요청의 정리 코드도 새 요청 참조를 지우지 않는다.
6. 주문 완료 화면은 기존 주문 ID를 현재 계정으로 다시 조회한다. 접근 불가 시 이전 내용은 숨긴 채 기존 안내/이동을 따른다.
7. 서로 다른 상품의 찜 등록·해제는 응답 시점의 최신 캐시에 해당 상품 변경만 반영한다. 동일 상품의 중복 요청 차단과 응답 소유자 검사는 유지한다.
8. 선물함·주문 완료 데이터 요청의 현재 계정 401은 상태를 비운 뒤 원래 주소(쿼리 포함)를 `redirect`로 보존해 로그인 화면으로 `replace` 이동한다. 이전 계정의 늦은 401은 폐기한다. 403의 기존 권한 안내/이동은 유지한다.

FE 재확인은 계정 변경 후 오래된 화면으로 조작하는 실수를 방지한다. 계정 확인과 다음 요청 사이에 세션이 바뀌는 극단적인 경쟁 조건을 원자적으로 막는 보장은 아니며, 실제 접근 권한은 기존 BE의 요청별 소유권 검사에 의존한다. 앱 전체의 실시간 계정 동기화나 이미 열린 리뷰 편집기까지 확장하는 작업은 아니다.

## 자동 검증

`npm test` (2026-09-29): 기존 78개 + `tests/account-switch.test.cjs` 37개 = **115개 통과**. Aon 리뷰 후 회귀 테스트 17개를 추가했다.

- 인증 요청 공유, 이전 인증 응답 폐기, 복귀 이벤트 중복 처리
- 통신 실패 시 계정 유지·재시도, 로그아웃 시 개인 상태 정리
- 찜 이전 조회/변경 응답 폐기, 계정 변경 후 POST/DELETE 차단
- 찜 목록 재구독, 캐시 대입 전 소유자 검사, 이전 401 리다이렉트 방지
- 알림 목록/상세 응답 폐기, 이전 ID 확인 요청 차단, 실패 후 명시적 재시도
- 이전 알림 확인 응답이 새 모달의 ID를 지우지 않음
- 선물함 계정/필터 변경 중 응답 순서 역전, 주문 완료 소유자 재확인
- 정상 찜 변경·알림 확인·동일 계정 주문 완료 재조회 유지
- 서로 다른 상품의 동시 등록/해제/등록+해제와 응답 순서 역전, 일부 실패, 같은 상품 연타
- 실제 `api.js` + 모의 fetch로 인증 확인 200 직후 데이터 401의 반환 주소/replace 검증
- 선물함·주문 완료의 이전 계정 401 폐기 및 403 기존 처리 유지
- 찜 목록·선물함·주문 완료의 인증 확인 503 시 새로고침 버튼과 강제 로그아웃 방지

신규 테스트는 실제 FE 스크립트에 DOM/HTTP 대역을 연결하고 응답 순서를 제어한다. 실제 BE·운영 DB 연동 테스트로 간주하지 않는다.

## 브라우저 확인 (2026-09-23)

실제 FE HTML/CSS/JS에 로컬 모의 API를 연결한 별도 환경에서 확인했다. 테스트 전용 버튼으로 서버 계정을 전환하고 탭 복귀 이벤트를 재현했으며, 운영 계정/DB에는 접근하지 않았다.

- 찜: A 상품/알림 → B 상품/알림으로 교체.
- 인증 확인 503: 기존 목록·알림을 지우고 재시도 안내, 강제 로그아웃 없음.
- 선물함: A의 목록/알림 → B의 목록/알림으로 교체.
- 주문 완료: A 주문 정상 표시 → B 전환 후 조회 404 → 이전 주문 비노출·안내 후 홈 이동.

## 실제 FE·BE 연동 후 수동 재확인

동일 브라우저의 두 탭에서 서로 다른 테스트 계정 A/B를 사용한다.

1. A로 `/wishlist`, `/giftbox`, `/complete?orderId=...` 또는 `orderGroupId=...`를 열어둔다.
2. 다른 탭에서 로그아웃 후 B로 로그인하고 기존 탭으로 복귀한다.
3. 찜/선물함은 B 데이터만 표시되고, A의 도착 모달·메시지·주문 결과가 유지되지 않는지 확인한다.
4. 전환 직전 눌렀던 찜·알림 확인 동작이 B 계정으로 자동 재실행되지 않는지 확인한다.
5. 로그아웃, 세션 만료, 뒤로가기 복원, 네트워크 중단/복구도 구분해 확인한다.

이 실제 두 탭 로그인·운영 환경 검증은 아직 수행하지 않았다.

## 후속 보완 수동 확인 / 병합 시 확인

- 찜한 서로 다른 상품 두 개를 빠르게 해제한 뒤 다시 등록할 때 목록/아이콘이 서버 상태와 일치하는지 확인한다.
- 인증 확인 후 데이터 요청이 401이면, 로그인 후 선물함 필터 또는 주문 완료의 주문 ID가 포함된 주소로 돌아오는지 확인한다.
- 인증 확인을 503으로 실패시킨 뒤 통신을 복구하고 세 화면의 새로고침 버튼으로 정상 조회되는지 확인한다.
- 위 후속 보완은 DOM/HTTP 대역 자동 테스트까지 확인했다. 실제 브라우저·BE 연동 확인을 완료한 것으로 간주하지 않는다.
- FE PR #105가 먼저 병합되면 develop을 반영해 로그인 이동을 해당 공통 처리와 맞추고 반환 주소·히스토리 테스트를 다시 실행한다. 이번 수정에서 #105 브랜치를 병합하거나 로그인 공통 API를 새로 만들지는 않았다.
